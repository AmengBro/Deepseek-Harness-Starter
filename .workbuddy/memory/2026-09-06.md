## 第二轮：iframe 跨源问题 → 切换 Tauri webview 标签

### 现象
截取 + emit 全部正常工作（日志里有 `[捕获] http://127.0.0.1:3080/?token=...`），前端 `iframe.src = url` 也对，但 iframe 加载 dsh 仍显示 **"authentication required; reopen the URL printed by dsh web"**。

### 根因
dsh rc 系列默认启用 token 认证，对**跨源 Origin 请求**（iframe 父页 Origin=tauri://localhost → 子页 http://127.0.0.1:3080）一律视为外站访问拒认证。证据来自社区 dsh-web-remote-access 插件文档说明。

iframe 是浏览器原生组件，无法绕过跨源检查；Tauri 1.x 的 `<webview>` 标签内部用原生 WebView2，不走 iframe 跨源 Origin 检查，dsh 接受。

### 修复
- `index.html`：在 `#webview-view` 里加 `<webview id="dsh-webview" src="about:blank" style="...">` 标签
- `App.ts::handleReady`：用 `document.getElementById("dsh-webview")` + `setAttribute("src", url)` 替换 iframe 创建逻辑；加 `console.log("[debug-handleReady]", url)` 和 `handleLog(\`[调试] handleReady 收到 URL: ${url}\`)` 调试输出；保留 iframe + no-referrer 兜底分支
- `dist/index.html` 含 `<webview>` 标签；`dist/assets/main-*.js` 含调试日志字符串

### build 过程踩的坑
- LNK1104 锁文件：用户之前开了 3 个 DeepseekHarness.exe 窗口（旧版本），全部 taskkill /F /T 才能让 link.exe 重新生成 deps exe
- bash `rm` 被 WorkBuddy bash 工具 hook 拦截（不是 Node shim，是工具层拦截），会触发 safe-delete fail-closed → 后续重新 build 时不删 deps 直接覆盖成功
- 切 Tauri webview 后 `grep exe` 找字符串失败：前端代码被 vite 编译到 `dist/assets/*.js`，要 grep dist 下的 js 而不是 exe 二进制

## 第三轮：iframe 跨源确认 → Tauri 1.x 不支持嵌入式 webview → 用 WindowBuilder 新窗口方案

### 现象
第二轮加了 `<webview>` 标签后跑新 exe，**webview 区域空白**。日志显示后端截取 + emit 完全成功，但前端 `<webview>` 标签是空元素（不渲染）。

### 根因（关键教训，下次别再踩）
- **Tauri 1.6.0 没有 `add_webview` 等嵌入式 webview API**（docs.rs/tauri/1.6.0/tauri/window/struct.Window.html 明确确认）
- **HTML `<webview>` 标签也不被 wry 识别**（那是 Electron 设计）
- `<webview>` 在 HTML 里就是个空自定义元素，浏览器不渲染 = "webview 空白"
- iframe 跨源问题（dsh RC 版本拒 iframe Origin 请求）依然存在

### Tauri 1.x 唯一稳定方案
用 `WindowBuilder::new(app, "dsh-web", tauri::WindowUrl::External(parsed_url))` 创建**独立新窗口**加载 dsh URL。新窗口走原生 WebView2，**没有 iframe 跨源 Origin 限制**，dsh 会接受带 token 的访问。

### 实施
1. `src-tauri/src/lib.rs` 加 `open_dsh_webview_inner` + `open_dsh_webview_window` tauri::command
2. 用 `tauri::Url::parse(url)`（不是 `url::Url::parse`，Tauri 1.6 re-export 为 `tauri::Url`）
3. invoke_handler 注册新 command
4. 前端 `tauri-api.ts` 加 `openDshWebviewWindow(url)` 方法（`invoke<void>("open_dsh_webview_window", { url })`）
5. `App.ts::handleReady` 改成调 `void this.api.openDshWebviewWindow(url).then().catch()`
6. `index.html` 移除 `<webview>` 标签（保留占位 div）
7. 主窗口 webview-view 显示"dsh web 已在独立窗口中显示"提示文字（用户能看到 dsh 已弹出）

## 第四轮 16:30：三个 bug 全修

### 用户反馈
1. "已在独立窗口显示"提示文字删了，主窗口只显示 webview
2. **关闭 dsh 窗口后重新打开主窗口**，要直接打开 dsh webview（不要从头走 spawn 流程）
3. 不稳定：有时 err，重启服务时**自动重弹 webview 但拒绝访问**

### 根因（从 applog 找到）
- applog 16:01 起每秒刷一条 "自动重启已达最大次数" → **monitor 死循环**。else 分支没 `break` 也未清空 child，下一次循环又 try_wait 同一个已退出的 child，每秒重复打 error
- **关 dsh 窗后打开主界面不弹 webview**：`start_service_internal` 入口没重置 `ready_emitted` / `auth_url`。重启服务后新 dsh 跑出来换了 token URL，但 `ready_emitted` 还是 `true` → read_pipe 抓到新 token 被 CAS 跳过 emit → 前端没收到 service-ready → 不弹窗口
- **重启服务后拒绝访问**：上面 bug 的表现 —— 旧 token URL 已失效，新 token 没传到前端，前端用旧 token 请求 → 拒绝访问
- PortProbe::Running（端口已被占用）路径直接 emit 裸 URL，没 spawn dsh 没 read_pipe 抓 token → 也可能是 "拒绝访问" 的一个原因

### 代码改动
1. `ServiceManager::reset_ready_state`（新建方法，service.rs:63）：重置 `auth_url=None / ready_emitted=false / restart_count=0`
2. `start_service_internal` 开头调用（service.rs:1063）
3. monitor else 分支加 `break` 跳出循环 + 日志改 "监控循环退出"
4. PortProbe::Running 路径：不再 emit `service-ready` 裸 URL，由 read_pipe 抓 token 后再触发
5. `App.ts::handleReady` 删 webview-view innerHTML 提示文字

### borrow check 遇到的坑
- `proc.as_mut()` 在 match arm 里借用了 proc 到 arm 结束 → 不能在 arm 里 mutate proc (`*proc = None`)
- 解法：drop 原 proc → 重新 lock → 清空 → break
- 简化：直接 `break` 出 loop，整个 task 死亡，process 锁自然释放，不用手动清空

### 真正根因 #2（潜在 bug，潜在触发拒绝访问）
`open_dsh_webview_inner` (lib.rs:281) 窗口已存在分支只 show+focus，**不 eval(newUrl) 跳转**。
即使 dsh 正常重启（换 token），旧 webview 仍加载旧 token URL → dsh 拒绝。
**当前未触发是因为根因 #1 把整个页面打不开**，但修 dsh 后这个 bug 会暴露。

### 修复
`lib.rs::open_dsh_webview_inner` 改造：
```rust
if let Some(window) = app_handle.get_window("dsh-web") {
    // 用 JSON.stringify 把 URL 字符串安全序列化进 JS，避免 token 含特殊字符被截断
    let js = format!(
        "window.location.replace({});",
        serde_json::Value::String(url.to_string())
    );
    if window.eval(&js).is_err() {
        // 极少情况 eval 失败（webview 还在加载中），关闭并重建
        let _ = window.close();
        std::thread::sleep(std::time::Duration::from_millis(100));
    } else {
        let _ = window.show();
        let _ = window.set_focus();
        return Ok(());
    }
}
```

```rust
fn auto_hide_main_window(app_handle: &AppHandle) {
    if let Some(window) = app_handle.get_window("main") {
        if window.is_visible().unwrap_or(false) {
            if window.hide().is_ok() {

            }
        }
    }
}
```

## 第九轮 22:07：检查更新无反馈 + 启动/退出时 cmd 黑窗

### 用户反馈

### 根因
- **无反馈**：`check_for_updates` 仅在"有更新"时 emit `update-available`；"已最新"返回 `None`、"出错"返回 `Err`，前端都没呈现 → 用户完全不知道是哪种状态。
- **cmd 黑窗**：启动/退出/打开设置时大量 spawn 子进程（dsh `cmd /c`、node 版本探测、where、taskkill、npm bin -g、pnpm、git、winget），但只有 dsh/npm install 几处加了 `creation_flags(0x08000000)`，其余都没加 → 一弹黑窗。

### 修复
1. `update.rs`：`check_for_updates` 新增 `UpdateCheckResult { latest, current, update_available, error }` 结构；用闭包 `report` 在**四分支**（未配置/网络错/有更新/已最新）都 emit `update-checked` 事件，携带 GitHub 最新版本号。比较用纯数字串 `version_greater(release_version, current_pure)`。
2. `tauri-api.ts`：加 `UpdateCheckResult` 接口 + `onUpdateChecked` 监听。
3. `App.ts`：注册 `onUpdateChecked` → `handleUpdateStatus`，三分支打到日志面板一行（"[更新] …GitHub 最新版本：vX.Y.Z（当前 vZ.Y.X）"）。⚠️ 本文件顶部 import 漏 `UpdateCheckResult` → 首次 build TS2304 报错，补 import 后通过。
4. `settings/main.ts`："检查更新"按钮下方插入 `#app-update-status` 状态行（内联样式，避免改 css 文件），监听 `update-checked` 渲染三态（已最新灰色 / 有更新绿色 / 错误红）；按钮文字改 confirm 替代原生 alert（Tauri 下原生 alert 不弹）。
5. `service.rs`：加 `use std::os::windows::process::CommandExt` + `hide_console(cmd: &mut AsyncCommand)` 辅助函数（Windows 加 `0x08000000`，非 Windows 空操作）；`check_node` 6 处探测 + taskkill×2 + dsh 启动×2 + where/版本探测共 10+ 处补 `creation_flags`。
