# 2026-09-05 工作日志

## DeepseekHarness 修复：dsh 端口参数传递 bug ✅

### 现象
- 程序启动后一直卡在 loading 视图，内嵌 webview 不出现
- 日志显示「等待服务就绪…」循环，直到 90 秒超时
- 用户体感："一直检测不到 3080 端口是否启动，一直无法启动内置 webview"

### 根因
`src-tauri/src/commands/service.rs` 的 `spawn_dsh_process` 用环境变量 `PORT` 传端口：

```rust
cmd.arg("web");
cmd.env("PORT", port.to_string())  // ❌ dsh 不读 PORT 环境变量
```

但 `dsh web`（即 `dsh --profile web`）**只认 `--port` 参数**，不读 PORT 环境变量。实测：

```
$ dsh web --help
Usage: dsh --profile web [options]
Options:
  --port <port>  listen port
  dsh --profile web --port 8080  serve on another port
```

### 后果链
1. dsh 启动成功但监听自己的默认端口（**不是 3080**）
2. 后端 `is_tcp_port_open(3080)` 一直 TCP 连接失败
3. 90 秒硬上限 → 日志打「服务启动超时，端口未能就绪」
4. 前端 `service-ready` 事件从头到尾没发过 → `handleReady` 不触发 → iframe 不创建 → 永远卡 loading
5. dsh 默认还会调起系统浏览器（用户体验割裂）

### 修复（已应用 + cargo check + cargo test 通过）
- 抽出 `configure_dsh_web_command(cmd, port) -> Command` 纯函数
- 把 `cmd.env("PORT", ...)` 改为 `cmd.arg("--port").arg(port.to_string())`
- 顺手加 `cmd.arg("--no-open")` 抑制默认浏览器弹窗
- `spawn_dsh_process` 改成调用 `configure_dsh_web_command`
- 加注释说明为什么必须用 `--port`（防回归）
- 加 2 个回归测试：`dsh_web_command_uses_port_flag_not_env`（顺序契约）+ `dsh_web_command_honors_custom_port`（防端口写死）
- 测试用 `Command::new("dsh")` 绕过 dsh 查找，跨平台可跑、不依赖 dsh 是否真安装

### 备份
- `src-tauri/src/commands/service.rs.bak.20260905`（原始版本，万一翻车可还原）

### 教训（重要）
- **启动子进程传参数前，必须先看真实 CLI 的 --help**，不能用「想当然」的环境变量
- 旧项目代码注释里写「npx @deepseek-ai/dsh web --port {port}（如果该工具支持 --port，否则需通过环境变量或配置文件）」——这个 fallback 思维本身就是坑的来源，下次类似场景要警惕
- 类似「传参后端口对不上」类 bug，**第一排查动作应是看子进程 stdout 的实际监听 URL**（dsh 启动后会有 `dsh web: http://127.0.0.1:XXXX/?token=...`），而不是看启动器侧配置

### 后续验证步骤（用户执行）
- `cargo tauri dev` 重跑，确认 3080 端口正确监听
- 查日志 `config/npmlog/npm-YYYY-MM-DD.log` 看 dsh 输出的实际 URL

## DeepseekHarness 修复：dsh web token 认证导致 iframe 显示 "authentication required" ✅

### 现象（端口修复后新出现）
- 端口修复生效：dsh 现在确实监听 3080（手动 `dsh web` 报 `EADDRINUSE 127.0.0.1:3080` 即证明）
- 但前端 iframe 显示：`dsh web authentication required; reopen the URL printed by dsh web`
- 根因：新版 dsh（npm 当前 0.1.2-rc.1，2 天前发）默认启用 URL token 认证，启动后打印
  `dsh web: http://127.0.0.1:3080/?token=xxx`，必须用该完整 URL（含 ?token=）访问
- 旧版（08-19 日志）打印的是无 token 的 `http://127.0.0.1:3080` —— 证实升级导致行为变化

### 原代码缺陷
- `start_service` 构造 `service-ready` 事件时 url 是 `format!("http://127.0.0.1:{}", port)`（裸 URL，无 token）
- `read_pipe` 只把 dsh stdout 原样转发日志，没解析 token URL
- 前端 `App.ts` `handleReady(url)` 直接 `iframe.src = url` → 裸 URL 被 dsh 拒绝认证

### 修复（已应用 + cargo check + 8 个测试全绿）
- `ServiceManager` 加 `auth_url: Arc<std::sync::Mutex<Option<String>>>` + `ready_emitted: Arc<AtomicBool>` 共享字段
- 新增纯函数 `extract_dsh_url(line) -> Option<String>`：从 stdout 行抓 `http://127.0.0.1:PORT...` 或 `http://localhost:PORT...`（含后续 ?token= 查询，截到空白/引号为止）
- `read_pipe`（spawn_blocking 同步线程）抓到 token URL 即写入 `auth_url` 并立即 emit `service-ready`（带 token），用 `ready_emitted` 防重复
- 探测循环（843/1051 两处，replace_all 改）TCP 就绪后**再等最多 8 秒**让 read_pipe 抓 token，最终 emit 时优先用 `auth_url`（无则裸 URL 兜底），`ready_emitted` CAS 防重复
- 加 4 个 `extract_dsh_url` 单元测试（带 token / 无 token / localhost+截断空白 / 无关行忽略）
